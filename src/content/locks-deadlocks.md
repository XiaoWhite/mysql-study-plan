InnoDB 在更新时会锁住相关索引记录。两个请求改同一件商品，一个事务先更新，另一个可能等待。多商品订单中，若两个事务以相反顺序更新，就可能互相等对方放锁。

## 用一条语句判断并扣减

```sql
-- 数量已在应用层验证为正整数。该例尝试购买商品 202 的 1 件。
UPDATE inventory
SET available = available - 1
WHERE product_id = 202 AND available >= 1;
```

| 步骤 | 请求 A | 请求 B |
| --- | --- | --- |
| 1 | 更新 202，命中 1 行，暂未提交 | |
| 2 | | 更新同一行，被 A 的锁阻塞 |
| 3 | 写订单和明细并提交 | |
| 4 | | 获得执行机会，条件已不满足，修改 0 行，回滚并报告缺货 |

若 A 回滚，则 B 可以命中一行。对于相同的请求数量，读库存、在 JS 计算新值、再用绝对值覆盖库存，会给并发请求留下用过期值的机会。优先使用主键条件缩小锁定范围。InnoDB 的范围访问还可能锁间隙，具体锁取决于隔离级别和计划。

## 处理死锁和超时

A 先锁 201 再锁 202，B 先锁 202 再锁 201。出现循环等待时，启用死锁检测的 InnoDB 会选择一个事务回滚，报 `ER_LOCK_DEADLOCK`（1213）。重试应从新事务开始，重新扣库存、写订单和明细。设定有上限的重试次数和短暂退避，保持外部支付等副作用幂等。

锁等待超时 `ER_LOCK_WAIT_TIMEOUT`（1205）的默认行为通常只回滚当前语句。应用应先回滚自己的完整事务，再根据业务决定是否重试。让批量更新统一按商品 ID 升序获取锁，减少这类循环等待。
